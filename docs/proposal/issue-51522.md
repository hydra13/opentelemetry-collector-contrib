# Proposal for issue #51522: propagate SQL row iteration errors

> [!IMPORTANT]
> This document is a working draft for the contributor to review and rewrite in
> their own words. It is not intended to be posted verbatim as an issue or pull
> request comment.

## Summary

`internal/sqlquery.DbSQLClient.QueryRows` iterates over `database/sql` rows but
does not check `Rows.Err()` after `Next()` returns `false`. As a result, an
iteration failure can be reported as a successful query, and callers may
consume an incomplete result set.

The proposed change exposes `Err()` through the package's private row
abstraction, checks it immediately after iteration, and treats a non-nil
iteration error as fatal. Partial rows would not be returned.

Tracking issue: [#51522](https://github.com/open-telemetry/opentelemetry-collector-contrib/issues/51522)

## Current behavior

`QueryRows` currently:

1. Calls `Next()` until it returns `false`.
2. Returns immediately when `Scan()` fails.
3. Accumulates recoverable `ErrNullValueWarning` values while converting rows.
4. Returns the accumulated rows and joined warnings after the loop.

The private `rows` interface in `internal/sqlquery/db_wrappers.go` does not
expose `Err()`, so `QueryRows` cannot distinguish normal exhaustion from a
driver, network, timeout, or context-cancellation error encountered during
iteration.

## Proposed behavior

Make the following focused changes:

1. Add `Err() error` to the private `rows` interface.
2. Implement `rowsWrapper.Err()` by delegating to `sql.Rows.Err()`.
3. Check `sqlRows.Err()` after the `Next()` loop and before returning accumulated
   NULL-value warnings.
4. Return `nil` together with the iteration error, preventing callers from using
   a result set whose completeness is unknown.

The iteration error should remain separate from `ErrNullValueWarning`.
`Scraper.ScrapeMetrics` treats errors matching `ErrNullValueWarning` as
recoverable; joining the fatal iteration error with such a warning could cause
the incomplete result to be treated as usable.

## Compatibility and scope

- The `rows` interface is private to `internal/sqlquery`; no public Go API changes.
- Successful queries retain their existing behavior.
- Existing NULL-value warning behavior remains unchanged when iteration ends
  normally.
- User configuration and receiver factories are unchanged.
- Handling errors returned by `Rows.Close()` is outside this proposal.
- No unrelated refactoring is included.

## Test plan

Add a regression test in `internal/sqlquery/db_client_test.go` by extending the
existing fake database and row implementations with a configurable iteration
error and an `Err()` method:

1. Return one valid row from `Next()` and scan it successfully.
2. End iteration on the following `Next()` call.
3. Return a sentinel iteration error from `Err()`.
4. Verify that `QueryRows` returns an error matching the sentinel through
   `errors.Is`.
5. Verify that the returned rows are `nil`, rather than the successfully scanned
   but incomplete partial result.

Also cover the case where a NULL-value warning is accumulated before the
iteration error. The fatal iteration error must take precedence, and no partial
rows should be returned.

Implementation will follow a red-green cycle: first demonstrate that the
regression test fails against the current behavior, then make the minimal
production change and rerun the focused and package-level checks.

## Validation plan

- Run the focused regression test.
- Run all tests for `internal/sqlquery`.
- Run lint for the affected module.
- Add and validate a bug-fix changelog entry for issue #51522.

## Maintainer agreement requested

Before implementation, please confirm these two semantics:

1. An iteration error is fatal even if one or more rows were scanned first.
2. `QueryRows` returns `nil`, not partial rows, when `Rows.Err()` is non-nil.
